# Capli 调研与首版建议

日期：2026-10-30。状态：研究与方案建议，未确认最终设计，未开始应用实现。

本次审阅了相关项目说明、部分实现源码和操作系统官方文档，没有安装运行竞品，也没有完成 Windows/macOS 实机技术验证。下文区分来源事实、产品判断与待验证假设。

## 1. 结论

建议将 Capli 定位为：为 AI Agent 提供真实桌面截图，并将截图加工成可直接交付文档流程的配图。

首版围绕“发现窗口 → 捕获 → Agent 看图确认 → 标注与裁剪 → 交付配图”闭环展开。以 CLI 为主要入口，提供使用说明；桌面辅助程序、MCP 和浏览器控制后续按实际需求增加。

这是基于竞争范围和实施复杂度的产品判断，不代表已经证明市场空白，也不保证开源传播或 Star 数。

## 2. 现有项目已经覆盖什么

| 项目 | 从项目文档核实的能力 | 对 Capli 的启示 |
| --- | --- | --- |
| [Peekaboo](https://github.com/openclaw/Peekaboo) | macOS CLI、菜单栏 App、屏幕捕获、辅助功能检查和原生 UI 自动化，也能暴露给 MCP 客户端 | “Agent 能截图”和“CLI + MCP”都已有先例；不宜首版就竞争完整桌面自动化 |
| [wgc-cli](https://github.com/vusiif/wgc-cli) | Windows 按标题、窗口句柄、进程等选择窗口，JSON 列表、裁剪缩放、诊断、MCP，以及不同会话下的本地桥接 | Windows 的简单 Agent 截图接口也已有方案；目标选择和错误恢复是基础要求 |
| [Playwright](https://playwright.dev/docs/screenshots) | 浏览器页面、完整页面及元素截图 | 网页捕获可由现有浏览器工具承担，不必先开发浏览器控制引擎 |
| [agent-browser](https://github.com/vercel-labs/agent-browser) | 面向 Agent 的浏览器 CLI，截图以及带编号的交互元素标注 | 自动编号并不是独有功能；文档中的选择性高亮、步骤编号及重新导出更适合作为待验证切口 |

上表不是穷尽性竞品清单，也没有据此断言这些项目缺少全部文档工作流。Capli 的价值仍需用实际任务和用户反馈验证。

## 3. 三种产品方向

| 方向 | 收益 | 代价 | 建议 |
| --- | --- | --- | --- |
| 统一截图 CLI | 范围小，容易解释 | 与现有工具重叠较多 | 作为底座，不作为全部产品价值 |
| 截图到文档配图的工具链 | 一个真实截图可以确认、重做标注、导出并用于多种文档 | 需要处理坐标、图像渲染和素材元数据 | 推荐首版方向 |
| 完整桌面智能体 | 可从打开软件一直执行到写完教程 | 需要规划、点击输入、状态恢复及更多权限 | 不纳入当前首版建议 |

## 4. 第一条验证任务

准备一个已打开的软件设置界面，要求 Agent 完成一份简短配置说明：

1. 枚举窗口，明确选定目标；同名窗口不能静默取第一项。
2. 截取三个真实界面状态。界面切换由用户或外部自动化工具完成。
3. Agent 读取图片，确认步骤与截图一致；文件存在本身不能证明内容正确。
4. 添加一处箭头、一处步骤编号和一处指定区域实色遮挡。
5. 导出图片和可正确解析的 Markdown 引用，完成说明文档。
6. 只修改标注参数重新导出，不重新截图。
7. Windows 和 macOS 分别完成同一个验收流程。

Markdown 是便于验证的首个交付格式建议。Word、飞书等格式由 Agent 对应的文档编辑工具接收图片；Capli 不把“返回图片路径”描述成“已插入文档”。

## 5. 建议的最小能力

### 5.1 目标发现与环境诊断

- `doctor`：报告运行环境、必要权限及该后端实际能力；提供结构化错误与恢复建议。
- `windows`：返回窗口 ID、应用、标题及可获得的状态；窗口 ID 仅是当前系统状态下的标识。
- 不默认采集所有窗口预览。只有选择了目标或显式请求预览时才捕获图片。

### 5.2 捕获与交付

- `capture`：明确指定窗口或显示器区域，输出 PNG 和素材元数据。
- 返回原图尺寸、坐标约定、平台后端和捕获时间；可另存小尺寸预览供 Agent 检查。
- 缺权限、目标关闭、窗口匹配不唯一、捕获超时、会话不可用分别返回错误；不能伪装成成功截图。
- 捕获时间及图片哈希用于记录来源和绑定标注，不证明画面已经完成业务加载。

### 5.3 文档配图加工

- `render`：读取原图和结构化标注文件，进行裁剪、缩放、箭头、编号和实色遮挡，再输出配图。
- 标注绑定原图的内容哈希，坐标使用原图像素；预览必须附带到原图的映射信息。
- 原图与处理图分开保存；明确原图仍可能包含被遮挡的信息，导出文档只引用处理后的图。
- 同一张原图上的裁剪与缩放由工具计算坐标转换，不要求 Agent 反复猜坐标。
- 标注位置的语义正确性仍需 Agent 看图确认。

建议保留 `original.png`、可选 `preview.jpg`、`annotations.json`、`figure.png` 和 `capture.json`；普通配图导出不自动打包原图。

以上是接口职责建议，不是已经可运行的命令或已冻结的参数设计。

## 6. Agent 接入契约

- JSON 包含 schema 版本、成功/失败状态、文件路径及必要元数据。
- stdout 保持机器可读，stderr 承载诊断信息；退出码与成功状态一致。
- 默认不把图像 Base64 文本倾倒进命令输出。CLI 返回文件路径，支持图像读取的 Agent 使用自己的图像工具查看。
- MCP 若增加，可返回图像内容，但共用捕获与渲染核心，避免两套逻辑。
- Skill 描述正确流程和错误恢复，不要求工具内部绑定模型账号。
- 远端 Agent 若不能访问本地图形会话，需要独立设计的本地桥接，不能因提供 CLI 就承诺任意远程截图。

## 7. 技术路线比较

| 路线 | 已核实事实 | 工程取舍 |
| --- | --- | --- |
| Go CLI + 原生平台适配 | Go 的 [kbinani/screenshot](https://github.com/kbinani/screenshot) 提供桌面/区域捕获和多显示器；README 明确 macOS 使用 cgo | 符合用户熟悉 Go 的背景；窗口枚举和窗口级捕获仍需平台实现，不能把屏幕区域截图当作窗口截图 |
| Rust CLI + XCap | [XCap](https://github.com/nashaofu/xcap) 提供屏幕与窗口捕获；示例跳过最小化窗口 | 可复用较多捕获接口，但需要维护 Rust，并验证实际系统/API 行为 |
| 封装现有 CLI | Peekaboo、wgc-cli 已有可调用接口 | 适合验证产品流程；额外安装、版本和行为差异会影响分发，不建议先把这种封装当作最终架构 |

目前倾向 Go 管理 CLI、素材元数据和渲染，平台适配层负责原生窗口枚举及捕获。最终选择应由双平台技术验证决定，暂不冻结依赖。

### 平台依据和具体发现

- Apple 的 [ScreenCaptureKit 官方示例](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) 说明可获得共享的显示器、应用和窗口，并构造窗口专用过滤器；[SCScreenshotManager](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager) 提供单帧图像捕获。
- Microsoft 的 [Windows.Graphics.Capture 文档](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) 描述窗口/显示器帧获取、支持检查和捕获生命周期；[CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow) 可用窗口句柄创建捕获目标。选择器流程和 Win32 互操作应区分，不能简单推断所有 CLI 捕获每次都必须人工选择。
- 审阅时 XCap 的 [macOS 捕获源码](https://github.com/nashaofu/xcap/blob/master/src/macos/capture.rs) 使用 `CGWindowListCreateImage`；这不是 ScreenCaptureKit 路线。这里仅记录实现事实，未据此断言它一定无法运行。
- XCap 的 [Windows 捕获源码](https://github.com/nashaofu/xcap/blob/master/src/windows/capture.rs) 根据 `wgc` feature 区分 WGC 与 GDI 路径，还处理 DPI 缩放。选择库后仍需选择和验证具体后端。
- Go 库的 [darwin.go](https://github.com/kbinani/screenshot/blob/master/darwin.go) 有 cgo 和系统框架依赖；不能承诺任意主机纯 Go 一条命令产出全部系统版本。

本报告审阅源码时使用了主分支，内容会随上游变更。正式采用依赖前需要固定版本并记录验证结果。

## 8. 首先要做的技术验证

不先开发完整桌面界面。优先验证下列四项：

1. macOS：授权前后枚举和捕获目标窗口，并验证发布程序身份变化后的权限行为。
2. Windows：窗口级捕获，并验证不同 DPI、多显示器以及 GPU 渲染应用。
3. 坐标：用已知位置的测试图，在原图、预览和导出图之间验证裁剪与标注映射。
4. 文档：Agent 读取截图后，插入 Markdown，检查引用、清晰度和标注位置。

遮挡、最小化、其他桌面/Space、锁屏和非交互会话分别记录实际结果；未支持时报告明确失败。首版不承诺静默恢复最小化窗口或改变用户焦点。

视觉稳定只能作为捕获等待的辅助信号，不能代替对“页面已加载正确内容”的判断。

## 9. 后续迭代顺序

1. 技术验证与接口约定：先确认真实窗口截图可用。
2. 最小闭环：CLI、Agent 使用说明、原图/预览/标注/配图、Markdown 示例。
3. 根据实际使用补充 MCP、安装授权辅助界面，以及浏览器截图导入。
4. 有明确需求后再增加特定文档适配器和更完整的桌面交互。

质量指标优先关注任务完成率、截图目标正确性、标注坐标正确性及错误能否恢复。费用、模型判断分数和大平台式评测不作为截图工具首版主线。

## 10. 仍待用户确认的范围

- 是否接受以“已有目标窗口的文档配图”为首个闭环。
- 实际最常用的目标软件及第一篇示例文档。
- 桌面辅助程序首版是否必须存在，还是先交付 CLI。
- 两套平台技术验证通过后，再确定最低系统版本和最终实现依赖。
